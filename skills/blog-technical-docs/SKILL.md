# Blog 技术文档写作指南

让简体中文读者既能准确对应英文技术概念，又能快速读懂文章。开篇先给英文术语、中文名称与简要解释；正文固定英文技术名称，用中文讲清关系、例子和取舍，用简短英文陈述已核实的核心事实。

## 开始前读取

本 Skill 随 `tcitry-blog` 站点工程保存，Markdown 内容在独立的 Blog 仓库中。

1. 从本 Skill 所在目录向上两级定位站点工程，读取其 `AGENTS.md`。按 `BLOG_DIR` 定位内容仓库；未设置时检查站点 `scripts/prepare-content.mjs` 的实际默认来源，不在站点 `docs/` 中误改 Blog 文章。
2. 读取内容仓库的 `Agents.md`，遵循其中当前有效的语言、分类、Git、AI 参与说明和 URL 兼容性规则。
3. 读取以下内容仓库内文件，建立本批参照：
   - `docs/Agents/technical-terminology-and-mermaid-style-guide.md`：完整规则、反例与验收方法。
   - `docs/Agents/contract-testing-cross-platform-ai-agents.md`：用户已验收的主要示范，包含导读、英文事实、中文推导、Mermaid 和可执行示例。
   - `docs/Agents/agent-led-development-testing-concepts.md`：多概念长文的辅助示范。

以上示范用于校准，不属于“其他文档”的默认改写范围。除用户明确要求或发现有证据支持的事实错误外，不再对已验收示范反复做语言重构。项目规则更新时以实际规则和用户当前要求为准，不复制示范的历史模型参数。

## 确定范围，逐篇判断

- 用户给出文件清单时严格按清单执行；只说“其他文档”时，先只读盘点 Blog 的 `docs/` 技术文档，优先近期新增或更新且存在术语混用、缺少导读或复杂关系难以理解的文章。
- 通常每批处理 3–5 篇相关文档；按内容长度调整。这是便于校验和回退的工作批次，不代表每批都需要再请求许可。用户授权持续处理时，逐批完成并推进；不要只交计划或问题清单。
- 通读本批原文，再建立编辑用的“固定英文名、中文对照名、待清理别名、概念边界”表。本文主题以外的名词不从示范强行引入。
- 不用全站字符串替换代替语义判断。Contract 与 Specification、Test Case 与 Test Vector、Test Oracle 与 Test Runner 各有职责，不能因为相关而合并。普通“客户端”也不一定指 Pact 的 Consumer。
- 发现并行任务留下的修改时保留它们；提交只包含本任务已审阅的文件或改动。不得替其他任务宣告验证或发布完成。

## 开篇：名称与解释都要有

在首次核心论述或密集使用专有术语之前，先给简短中文导语，再放读者参考表。必须同时有三个信息项，不能只解释作用而缺少中文名称。

```markdown
<div class="reader-glossary">

| 英文术语 | 中文名称 | 简要解释 |
| --- | --- | --- |
| Contract Testing | 契约测试 | 检查两个系统交换的数据是否符合双方约定 |
| Test Oracle | 测试预言机 | 判断实际结果是否符合预期的依据或机制 |

</div>
```

- 中文名称用通行译名或准确直译；解释用一句普通中文，必要时带一个小例子。不能用另一串未解释的英文词循环定义。
- 导读中的中文名称是帮助对应词义，不必声称它是官方中文名称。Mermaid 等产品名没有合适译名时保留原名，不生造名称。
- 优先覆盖标题、开篇和第一张图中的关键陌生术语。长文的新概念可以在对应小节首次展开时补充局部对照，不在开头堆完整词典。
- 保留 `<div class="reader-glossary">` 包裹和表格前后的空行。本站 `src/styles/blog.module.css` 负责三列桌面布局及窄屏的术语分组，不把 CSS 复制进文章。
- **中文名称限于导读对照；正文与 Mermaid 继续使用固定英文名。** 别名搜索必须保留这些有意出现的中文名称，也要区分正反例与原始引用。
- 读者参考表与编辑用别名清单用途不同。不要把查错清单放在文章开头充当解释。

## 正文：英文准确，中文顺畅

- 产品、功能、API 和专有概念采用核实后的英文名称，统一大小写和指代；不要在同一概念的英文名、中文译名、自造简称之间轮换。英文语法需要的单复数变化不等于别名。
- 官方定义、API 约束、关键机制等能用一两句说清的已验证事实，用自然完整的英文表达，再用中文解释场景含义、关系和取舍。转述与直接引文分清，来源紧随事实。
- 背景、类比、推导和日常动作继续用中文；数据库、缓存、重试等自然中文不用机械换成英语。不要随机把英文动词塞进中文句子，也不要逐句中英重复。
- 标题、小标题、正文、图表、图注、链接显示文字和 Prompt 共用同一套技术名称。只改变表述时不改技术结论或删去前提。

## 事实与 Context7

涉及库、框架、SDK、API、CLI 或云服务的名称、能力、配置和版本时，按 Blog 的 Context7 约定阅读当前文档，即使记得用法也要核对。

- 优先 `ctx7` CLI：先用 `library` 解析 ID，再按独立概念用 `docs` 查询；命令形式、版本匹配、调用预算及 sandbox 要求沿用 Blog 的实际规则。
- 复用本批已取得的有效证据，核对定义、保证、前提与限制。公开引用落到官方原始页面，不只给 Context7 检索入口。
- Context7 未收录的规范、论文或资料直接核对一手来源。无法查证时明确保留未解决项，不用记忆补出权威结论；不要因额度顾虑省略必要查询。
- 纯语言调整、一般概念关系或未变更的图表不需要为使用工具而重复查询。

## Mermaid：帮助理解关系

对多步流程、交互、状态转换或概念关系，主动判断是否可以用一张图替代重复的长段说明。

- 根据问题选 flowchart、sequenceDiagram 或 stateDiagram-v2 等图形。flowchart 默认 TB / TD；仅在结构很短且仍易读时使用横向布局。
- 一图回答一个主要问题，保持节点短、标签完整；过密时拆图或调整换行，不靠缩小字体容纳整篇文章。
- 节点和消息名复用正文英文名称；关系、动作与图注可使用中文。保留必要的条件、失败分支和边界，不用箭头凭空增加因果、顺序或调用关系。
- 图已清楚表达的步骤可从正文删减；解释为什么、何时适用及例外的文字保留。没有必要画图的短说明不强行加图。
- 若当前环境已安装 `design-doc-mermaid`，可读取其有助于当前任务的指南；不因它的模板擅自新增目录或把原生 Mermaid 全部转成图片。不把社区 Skill 称为官方 Skill。

## 内容与工程边界

- 保留 slug、permalink、aliases、URL、文件路径、现有 draft 状态和官方 API / 协议字段。标题确需更改时，按 Blog 的 Giscus pathname 规则检查；语言整理不应顺手迁移页面或发布既有草稿。
- 若自包含教学示例自己的字段误用了概念，同步数据、代码、错误提示与预期输出，并重新运行。外部接口标识不能随正文改名。
- 直接修正目标原文；不另写一篇纠错清单代替修改。保持现有目录与标签，遵守项目对新建目录的限制。
- 改写后的正文应能独立阅读，不插入“原文把……叫作……”或“本次将……统一为……”等编辑过程说明；这些决定放在任务报告中，正文直接解释最终概念和关系。
- 内部链接用 Blog 当前支持的 relref 约定，不改成 Obsidian 双链或未经转换的相对 Markdown 链接。核对生成 HTML 的最终链接及强调。
- 保留历史 AI 参与记录，补充本次范围及可核验的当前运行元数据；缺失信息不猜填，不复制示范中的模型和 effort。

## 每批验收与交接

1. 检查完整 diff，搜索别名并逐项判断；确认导读三项齐全、正文术语一致、不同概念未被合并、中文自然。
2. 运行发生变化的可执行示例。依据站点当前 `package.json` 完成适用的 build、check、test、verify，不使用旧 Hugo 命令。
3. 检查 Astro 生成的实际 HTML 与最终 URL。用浏览器确认参考表在桌面和 320 / 390px 等窄屏都能对应英文、中文名称与解释；不能只确认整页没溢出，却让解释藏在横向滚动区。
4. 检查 Mermaid 实际生成 SVG、无语法错误、标签完整、图文关系正确；源码通过搜索不代表渲染验收通过。
5. 简短报告本批文件、术语决定、图解变化、实际验证和未解决项。按用户授权继续下一批；批次状态放在任务记录中，不把执行待办混入公开文章。

提交、推送与部署遵循当前任务授权和仓库约定；本 Skill 不新增发布权限，也不增加无根据的确认步骤。发布时使用固定内容提交和独立站点检出，按当前生产命令验证并验收线上结果；不能从并行任务可能改写的共享 `dist/` 发布，不能把 Git 推送当作网站上线。
